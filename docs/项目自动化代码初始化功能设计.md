# 项目自动化代码初始化功能设计

> 版本：v1.1（按确认结果修订）
> 关联模块：项目管理（`projects`）、Python 环境管理（`python_envs`）、自动化用例文件生成（`auto_file_service`）

---

## 1. 需求背景与目标

### 1.1 现状

当前「新增项目」只登记元信息与两个路径：

- `auto_root_path`：自动化测试根路径，即 pytest 的 **tests 目录**，由用户在弹窗里手工填写。
  用例文件由 `auto_file_service.generate_automation_file()` 按
  `<auto_root_path>/<module_code>.py` 直接写入。
- `python_path`：执行 pytest 用的解释器路径，由
  `auto_exec_service._run_pytest_async()` 调用。

**问题**：目录结构和依赖环境完全依赖用户离线手工准备，平台不参与。

### 1.2 目标

在「新增项目」时增加一次性的**代码初始化**能力：

1. 全局自动化根目录（BASE_DIR）由**配置文件**决定，用户不可填写；
2. 用户只需在弹窗里选 `python_path` + 上传自动化代码 zip；
3. 校验 zip 内**恰好一个顶层目录**（记作 `<proj_dir>`），且其中**存在 `tests` 目录**；
4. 把 `<proj_dir>` **原样保留这一层**投放到 `{BASE_DIR}/<proj_dir>/`；
5. 自动推导并回写 `projects.auto_root_path = {BASE_DIR}/<proj_dir>/tests`；
6. 用该项目的 `python_path` 执行 `pip install -r {BASE_DIR}/<proj_dir>/requirements.txt`。

### 1.3 非目标

- 不做代码增量更新/版本管理（重新初始化是覆盖式重放，见 §7.3）。
- 不校验压缩包内代码的语法或可运行性。
- 不做 git 仓库拉取（仅 zip 上传）。
- 不做 pip 镜像源配置（按确认：直接用用户所选 `python_path` 的 pip 默认源）。

## 2. 名词与现有代码锚点

| 名词 | 含义 | 现有代码 |
| --- | --- | --- |
| 全局自动化根目录 BASE_DIR | 所有项目代码包的统一存放父目录，来自配置文件 | 本设计引入 `PROJECT_CODE_BASE_DIR` |
| 项目目录 `<proj_dir>` | zip 内唯一顶层目录名，如 `meterbot` | 本设计引入 |
| 项目根 | `{BASE_DIR}/<proj_dir>`，`requirements.txt`/`pytest.ini` 所在层 | 本设计引入 |
| 自动化根路径 | `{BASE_DIR}/<proj_dir>/tests`，写回 `projects.auto_root_path` | `projects.auto_root_path` |
| Python 路径 | 执行 pytest / pip 的解释器，用户从「Python 环境管理」下拉选择 | `projects.python_path` |
| 路径校验 | 必须是已存在且可写的目录 | `auto_file_service.validate_root_path()` |
| 异步行下发 | `asyncio.create_task` + 强引用，接口立即返回 | `testcase_sync_service.dispatch_project_sync()` |
| 子进程执行 | `create_subprocess_exec` + `wait_for` + 超时 kill | `auto_exec_service._run_pytest_async()` |
| 条件更新认领 | 多 worker 下防重复执行 | `python_env_service._claim()` |

## 3. 总体流程

```
用户在「新增项目」弹窗填写：
  code / name / owner / python_path(下拉)  +  选择 zip
  （不再填写 auto_root_path）
        │
        ├─(1) POST /projects                      JSON，创建项目（code_init_status='none'）
        │
        └─(2) POST /projects/{id}/code            multipart，上传 zip 并触发初始化
                    │
                    ├─ 同步阶段（接口内，< 1s，任一失败直接返回且不留半成品）
                    │   ① 校验项目存在、状态未被占用
                    │   ② 校验 PROJECT_CODE_BASE_DIR 已配置且存在可写
                    │   ③ 校验 python_path 可用
                    │   ④ 分块落盘 zip 到临时目录（超限即中断）
                    │   ⑤ zipfile 打开，做安全检查（§5、§6）
                    │   ⑥ 解析顶层目录 → <proj_dir>，校验 <proj_dir>/tests 存在
                    │   ⑦ 条件更新 code_init_status: -> 'pending'
                    │
                    └─ 异步阶段（后台任务，接口已返回）
                        ⑧ 解压到 <tmp>/<uuid>/staging
                        ⑨ staging 内复检结构
                        ⑩ 投放：staging/<proj_dir>/** → {BASE_DIR}/<proj_dir>/**
                                 （同名覆盖、异名保留）
                        ⑪ 回写 auto_root_path = {BASE_DIR}/<proj_dir>/tests
                        ⑫ pip install -r {BASE_DIR}/<proj_dir>/requirements.txt
                           （cwd = {BASE_DIR}/<proj_dir>）
                        ⑬ 写回状态/日志/时间/触发人
                        ⑭ finally 清理临时目录（zip + staging）
```

**为什么分两个接口而不是把 zip 塞进 `POST /projects`**

`POST /projects` 现在是纯 JSON（`ProjectCreate`），改造成 `multipart/form-data` 会破坏既有契约
（OpenAPI 文档、`ProjectCreate` 字段校验、可能的 API Key 调用方）。拆成"建项目 → 传代码"两步：

- 前端在同一个弹窗里串行调用，用户体感仍是一次操作；
- 复用 `ProjectCreate` 的字段校验；
- 初始化可**单独重跑**，无需重建项目。

## 4. 目录映射规则（本功能核心）

### 4.1 压缩包结构与投放结果

配置文件：

```env
PROJECT_CODE_BASE_DIR=/var/www/test_platform/test_project
```

压缩包结构：

```
meterbot.zip
└── meterbot/                     ← 唯一顶层目录 = <proj_dir>
    ├── tests/                    ← 必须存在
    │   ├── conftest.py
    │   └── test_login.py
    ├── requirements.txt
    └── pytest.ini
```

投放结果：

```
/var/www/test_platform/test_project/          ← BASE_DIR（已存在，不创建）
└── meterbot/                                 ← 原样保留这一层
    ├── tests/
    │   ├── conftest.py
    │   └── test_login.py
    ├── requirements.txt
    └── pytest.ini

projects.auto_root_path = /var/www/test_platform/test_project/meterbot/tests
```

| zip 内路径 | 投放目标 |
| --- | --- |
| `meterbot/tests/conftest.py` | `/var/www/test_platform/test_project/meterbot/tests/conftest.py` |
| `meterbot/requirements.txt` | `/var/www/test_platform/test_project/meterbot/requirements.txt` |
| `meterbot/pytest.ini` | `/var/www/test_platform/test_project/meterbot/pytest.ini` |

> **关键点：`<proj_dir>` 这一层必须保留，不能消层。**
> 这样才与现有 `generate_automation_file()` 的写入位置一致——它把 `<module_code>.py`
> 写在 `auto_root_path`（即 `.../meterbot/tests`）下，而不是 `.../meterbot/tests/tests/` 下。

### 4.2 顶层目录的识别规则

1. 遍历 `ZipFile.infolist()`，取每条路径的第一段，得到"顶层条目集合"；
2. **过滤打包噪音**：`__MACOSX`、`.DS_Store`、`Thumbs.db`、`desktop.ini`；
3. 过滤后把所有顶层目录收集为候选，**必须恰好 1 个** → 记作 `<proj_dir>`；
   - 一个都没有 → 400 `压缩包内未找到项目文件夹，请把整个项目文件夹（内含 tests 目录）打包后上传`
   - 多于 1 个 → 400 `压缩包顶层存在多个文件夹（a、b），请只打包一个项目文件夹`
4. 顶层**散落的文件**（如误拖进来的 `readme.txt`）不参与上述判定，也**不会被投放**，
   仅在日志中记录一条"已忽略压缩包顶层散落文件"；
5. `<proj_dir>` 名称合法性：`^[A-Za-z0-9._-]{1,100}$`，且不为 `.` / `..`；
6. `<proj_dir>` 小写等于 `tests` 时，判定为"把文件夹内容而非文件夹本身打了包"，
   给同样的 400 提示（否则会报出"项目文件夹 tests 内未找到 tests 目录"这种费解信息）；
7. `<proj_dir>/tests` 必须存在，否则 400 `项目文件夹 <proj_dir> 内未找到 tests 目录`。

### 4.3 requirements.txt 查找顺序

取第一个命中：

1. `{BASE_DIR}/<proj_dir>/requirements.txt`（项目根，常规位置）
2. `{BASE_DIR}/<proj_dir>/tests/requirements.txt`

都没有 → **不算失败**：`code_init_status=ready`，日志记
`未找到 requirements.txt，跳过依赖安装`。

执行时 `cwd = {BASE_DIR}/<proj_dir>`，使 `requirements.txt` 里的相对引用（如 `-e .`）可正确解析。

### 4.4 目标目录已存在的处理（重新初始化）

按确认：**同名覆盖、异名保留，不预清理**。

- 逐条写文件，路径已存在的直接覆盖；
- 压缩包里没有、但磁盘上已存在的老文件**不删除**（删掉的用例文件会残留，已知代价）；
- 例外：若 `{BASE_DIR}/<proj_dir>` 已被**另一个项目**登记为路径
  （即存在 `other_project.auto_root_path LIKE '{BASE_DIR}/<proj_dir>/%'`）→ 409
  `该目录已被项目「X」使用，请更换项目目录名或先清理`。

## 5. 压缩包校验规则

全部在同步阶段完成，通过后才落 `pending`：

| 编号 | 校验项 | 不通过时 |
| --- | --- | --- |
| V1 | `file` 存在且 `filename` 以 `.zip` 结尾 | 400 `请上传 .zip 压缩包` |
| V2 | `zipfile.ZipFile` 能正常打开（捕获 `BadZipFile` / `LargeZipFile`） | 400 `压缩包已损坏或不是合法的 zip` |
| V3 | 条目数 ≤ `PROJECT_CODE_MAX_FILES` | 400 `压缩包文件数超过限制` |
| V4 | `sum(zi.file_size)` ≤ `PROJECT_CODE_MAX_UNCOMPRESSED_MB` | 400 `压缩包解压后体积超过限制` |
| V5 | 条目路径不含绝对路径、`..`、盘符 | 400 `压缩包内存在非法路径: <entry>` |
| V6 | 条目不是符号链接（`external_attr >> 16` 的 `S_ISLNK`） | 400 `压缩包内存在符号链接，已拒绝` |
| V7 | 无重复条目名 | 400 `压缩包内存在重名条目: <entry>` |
| V8 | 顶层恰好一个目录 = `<proj_dir>`（§4.2） | 400，见 §4.2 文案 |
| V9 | `<proj_dir>/tests` 存在（§4.2） | 400 |
| V10 | `<proj_dir>` 名称合法（§4.2） | 400 `项目目录名不合法: <proj_dir>` |

> V3/V4 用 `infolist()` 的元数据判定，**不解压即可拒绝**，避免"先被撑爆再报错"。

## 6. 安全设计

### 6.1 Zip Slip（路径穿越）——最高优先级

恶意 zip 可含 `../../etc/passwd`、`C:\autoexec.bat`。**双保险**：

1. **入口拦截**：逐条规范化路径，含 `..` 段、绝对路径、盘符 → 直接拒绝（V5）；
2. **出口复检**：解压时逐条 `target = (staging / rel).resolve()`，用
   `target.is_relative_to(staging.resolve())` 断言在允许范围内，越界即中止并清理 staging。
   投放阶段再从 staging 拷到 `{BASE_DIR}/<proj_dir>`，同样做一次目标范围断言。

**不使用 `ZipFile.extractall()`**——它无法逐条做目标路径断言。

### 6.2 Zip Bomb

- 入口按 `sum(zi.file_size)` 预判总体积与条目数（V3/V4）；
- 解压过程中累计实际写入字节，超限立即中止并清理 staging。

### 6.3 上传体积

`UploadFile` 是流式的，**不能先读进内存**。1MB 分块 `await file.read(1MB)` 边写盘边累加，
超过 `PROJECT_CODE_UPLOAD_MAX_MB` 即中断并删除临时文件（防磁盘打满）。

### 6.4 命令执行边界（必须知情）

用项目的 `python_path` 执行 `pip install -r requirements.txt`，本质是**在服务器上运行用户提供的代码**
（`setup.py` / PEP 517 构建后端会在安装期执行）。这是功能固有属性，缓解措施：

- `python_path` 白名单式校验：文件存在、是文件、可执行（§9.1 `validate_python_path`）；
- 命令用 `create_subprocess_exec(*args)` 传参，**绝不拼字符串走 shell**，避免命令注入；
- 附加 `--disable-pip-version-check`；
- 接口挂独立权限 `project:init`，只授予可信角色；
- 投放目标必须在 `PROJECT_CODE_BASE_DIR` 内（`..` 与绝对路径均被拒），防止写到系统目录。

> 结论：该功能应视为**受信操作**。若要面向不可信用户，需引入容器化隔离，本设计不覆盖。

## 7. 异步任务与状态机

### 7.1 状态定义（`projects.code_init_status`）

| 状态 | 含义 | 进入方式 |
| --- | --- | --- |
| `none` | 未初始化（默认值，含存量数据） | 迁移默认值 |
| `pending` | 已受理，等待后台任务认领 | 上传接口同步校验通过 |
| `extracting` | 正在解压 + 投放 | 后台任务条件更新认领 |
| `installing` | 正在 `pip install` | 解压投放成功后 |
| `ready` | 初始化完成 | pip 成功 或 无 requirements.txt |
| `failed` | 失败（可重试） | 任一环节异常 |

### 7.2 状态流转图

```
none ──上传──▶ pending ──认领──▶ extracting ──▶ installing ──▶ ready
  ▲               │                  │               │
  └───────────────┴──────────────────┴───────────────┴──▶ failed
                                              （重新上传可再次进入 pending）
```

### 7.3 并发与幂等

- **认领**：`UPDATE projects SET code_init_status='extracting'
  WHERE id=:id AND code_init_status='pending'`，影响行数 0 说明已被其他 worker 抢先，直接放弃
  （沿用 `python_env_service._claim()` 写法，适配多 worker 部署）。
- **上传时占用检查**：状态属于 `{pending, extracting, installing}` → 409
  `该项目代码正在初始化中，请稍后再试`。
- **重新初始化**：`ready` / `failed` / `none` 下均可再次上传，覆盖语义见 §4.4。

### 7.4 回滚策略

采用 **staging 暂存区 + 后投放**，降低风险但不保证跨文件系统原子：

1. 解压到 `<tmp>/<uuid>/staging`，**目标目录此时完全未被触碰**；
2. staging 内复检结构（§4.2）后再投放；
3. 解压/校验阶段失败 → 目标目录零改动，直接 `failed`；
4. **投放成功后** `pip install` 失败 → **不回滚已投放的代码**，仅置 `failed` 并保留 `code_init_log`。
   理由：代码是合法产物；回滚需删除可能已覆盖的用户文件，风险高于收益。用户修好依赖后
   可直接点「重新初始化」或 §9.3 的「仅重跑依赖安装」。

## 8. 数据模型变更

### 8.1 迁移 `0007_project_code_init`（`down_revision = "0006_python_envs"`）

`projects` 表追加 5 列：

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `code_init_status` | `VARCHAR(20)` | `NOT NULL, server_default='none'` | 状态机 |
| `code_init_error` | `TEXT` | NULL | 失败原因（单行摘要，供 tooltip） |
| `code_init_log` | `TEXT` | NULL | 最近一次完整输出（截断见 §8.3） |
| `code_init_at` | `TIMESTAMP` | NULL | 最近一次完成时间 |
| `code_init_by` | `INTEGER` | NULL, FK `users.id ON DELETE SET NULL` | 触发人 |

索引：`ix_projects_code_init_status`。

### 8.2 `auto_root_path` 的语义变更

- **不再由用户填写**：`ProjectCreate` / `ProjectUpdate` **移除** `auto_root_path` 字段
  （前端输入框同步移除，改为只读展示）；
- **只由初始化任务写入**：`{BASE_DIR}/<proj_dir>/tests`；
- `ProjectResponse` **保留**该字段（只读），老数据原值不动；
- 初始化前为 `NULL`，此时「用例同步」「用例文件生成」按既有逻辑拒绝
  （`ensure_sync_ready()` 已有 `该项目未配置自动化根路径` 提示），无需额外改动。

> 项目根（pip 的 cwd、requirements.txt 位置）不需要单独存字段，由
> `Path(auto_root_path).parent` 推导即可。

### 8.3 `code_init_log` 截断

上限 100,000 字符，保留**尾部**（pip 报错在尾部），头部加 `...（前部已截断）` 标记。
量级与 `auto_exec_service._MAX_LOG_CHARS` 保持一致。

### 8.4 为什么不用独立表

一个项目同时只有一次初始化，且状态要跟项目列表一起展示/轮询；放 `projects` 上避免列表接口额外 join。
代价：**没有多次初始化历史**。若后续需要审计，再拆 `project_code_init_logs`
（类似 `case_execution_logs`），本设计不预先引入。

## 9. 接口设计

统一前缀 `settings.API_V1_PREFIX`（`/api/v1`），沿用 `Response.success/error` 包装。

### 9.1 新增：上传代码并触发初始化

```
POST /projects/{project_id}/code
Content-Type: multipart/form-data
Body: file=<zip 文件>
权限: project:init
```

**成功响应**：

```json
{ "code": 200, "message": "代码初始化任务已提交，请稍后查看结果",
  "data": { "project_id": 12, "code_init_status": "pending" } }
```

**同步阶段执行顺序**（任一失败立即返回）：

1. 取项目 → 不存在 404；
2. `code_init_status` 占用检查 → 409；
3. `PROJECT_CODE_BASE_DIR` 未配置 → 400 `未配置项目代码全局根目录`；
   `validate_root_path(BASE_DIR)` 失败 → 400；
4. `validate_python_path(python_path)`：
   - 未配置 → 400 `请先配置 Python 解释器路径`
   - 文件不存在 / 不是文件 / 不可执行 → 400 `Python 解释器路径无效: <path>`
5. 分块落盘 zip（§6.3）；
6. 打开 zip 做 V1–V10 校验，解析出 `<proj_dir>`；
7. 检查 `{BASE_DIR}/<proj_dir>` 是否被其他项目占用（§4.4）→ 409；
8. 置 `pending` + `code_init_by` + `code_init_error=NULL`，`commit`；
9. `dispatch_project_code_init(project_id)`。

> 第 8 步**必须 commit 之后再下发任务**，否则后台任务用新 session 读不到该行。

**`<proj_dir>` 传递方式**：接口解析出后随任务一起传入
`dispatch_project_code_init(project_id, proj_dir, tmp_zip_path)`，避免后台任务重复解析 zip。

### 9.2 查询状态

不新增接口，状态通过既有接口获取：

- `GET /projects`（列表：表格「代码初始化」列 + 轮询）
- `GET /projects/{id}`（详情/弹窗：展示 `code_init_log`）

`ProjectResponse` 新增只读字段：

```json
"code_init_status": "installing",
"code_init_error": null,
"code_init_log": "...",
"code_init_at": "2026-09-14T10:20:31",
"code_init_by": 1
```

### 9.3 新增：仅重跑依赖安装

```
POST /projects/{project_id}/code/install
权限: project:init
```

用途：`failed` 且原因是 pip 失败时，免去重传大包。

校验：`code_init_status == 'failed'` 且磁盘上能定位到 `requirements.txt`（§4.3 顺序），
否则 400 `未找到 requirements.txt 或当前状态不允许重试`。

行为：置 `installing` → 后台执行 pip → 回写状态。

## 10. 配置项（`app/config.py` + `.env`）

```python
# ==================== 项目自动化代码初始化 ====================
# 全局自动化根目录：所有项目代码包统一存放于此，解压出的项目文件夹作为其子目录。
# 该目录需预先存在且可写；每个项目的 auto_root_path = {BASE_DIR}/<项目目录名>/tests
PROJECT_CODE_BASE_DIR: str = ""
# 上传 zip 大小上限（MB）
PROJECT_CODE_UPLOAD_MAX_MB: int = 200
# 解压后总体积上限（MB），防 zip bomb
PROJECT_CODE_MAX_UNCOMPRESSED_MB: int = 2000
# 压缩包条目数上限
PROJECT_CODE_MAX_FILES: int = 20000
# pip install 超时（秒）；依赖多时可能很久
PROJECT_CODE_INIT_TIMEOUT: int = 1800
# 临时目录；为空用系统临时目录
PROJECT_CODE_TMP_DIR: str = ""
```

`.env` / `.env.example` 同步补占位（与 `CONDA_*` 写法一致）：


### 11.3 `api/project.js`

```js
export function uploadProjectCode(projectId, file) {
  const form = new FormData()
  form.append('file', file)
  return request.post(`/projects/${projectId}/code`, form, {
    headers: { 'Content-Type': 'multipart/form-data' },
    timeout: 0        // 大包上传不能受 axios 全局 15s 超时限制
  })
}

export function reinstallProjectCodeDeps(projectId) {
  return request.post(`/projects/${projectId}/code/install`)
}
```

> **易踩坑**：`api/index.js` 的 axios 实例是 `timeout: 15000`。上传大包必须显式覆盖
> `timeout`（0 = 不超时），否则必然超时并误报"网络错误，请检查网络连接"。

## 14. 边界与异常清单

| 场景 | 预期行为 |
| --- | --- |
| 上传非 zip / 改后缀的假 zip | V1/V2 拦截，400 |
| zip 顶层无目录（直接是 `tests/`） | V8 拦截，400，提示"请把项目文件夹整体打包" |
| zip 顶层多个目录 | V8 拦截，400，列出冲突目录名 |
| `<proj_dir>` 内无 `tests` | V9 拦截，400 |
| `<proj_dir>` 名含 `/`、`..`、非法字符 | V10 拦截，400 |
| zip 内 `../` 越界条目 | V5 入口拦截 + 出口复检，400 |
| zip 解压后超 2GB | V4 预判或解压中累计拦截，中止并清理 staging |
| 上传中断网 | `finally` 统一清理临时文件；建议启动时清理 >24h 的残留（可后置） |
| `PROJECT_CODE_BASE_DIR` 未配置 | 400 `未配置项目代码全局根目录` |
| BASE_DIR 不存在 / 不可写 | 400，提示具体路径（复用 `validate_root_path`） |
| 项目无 `python_path` | 400 `请先配置 Python 解释器路径` |
| `python_path` 指向不存在的文件 | 400 `Python 解释器路径无效` |
| `{BASE_DIR}/<proj_dir>` 已被其他项目占用 | 409 `该目录已被项目「X」使用` |
| 目标目录已有同名文件 | 同名覆盖、异名保留（§4.4） |
| `requirements.txt` 不存在 | 跳过安装，`ready` + 日志说明 |
| pip 安装失败（依赖冲突/网络不通） | `failed`，`code_init_error` 取输出尾部摘要，代码保留 |
| pip 安装超时（>30min） | 杀进程，`failed`，日志注明超时 |
| 后台任务认领失败（多 worker 竞争） | 静默退出，记 info 日志 |
| 服务器重启时任务进行中 | 状态卡在 `extracting`/`installing`，用户可重新上传覆盖（本次不引入僵尸状态自动复位） |
| zip 内中文文件名乱码（Windows GBK 打包） | 解压时若 `flag_bits` 未置 UTF-8，尝试 `name.encode('cp437').decode('gbk')` 兜底，仍失败用原名 |
| Windows 超长路径（>260） | 记录日志告警；必要时用 `\\?\` 前缀 |
| 存量项目 `auto_root_path` 已手填 | 不迁移、不覆盖；下次上传初始化时会按新规则重写 |

## 15. 已确认决策记录

| # | 决策点 | 结论 |
| --- | --- | --- |
| 1 | 全局自动化根目录来源 | 放配置文件 `PROJECT_CODE_BASE_DIR`，用户不可填写 |
| 2 | 目录映射 | **保留** zip 顶层目录层：`<proj_dir>/**` → `{BASE_DIR}/<proj_dir>/**`；`auto_root_path = {BASE_DIR}/<proj_dir>/tests` |
| 3 | 顶层目录结构 | 必须恰好一个顶层目录（噪音项如 `__MACOSX` 先过滤） |
| 4 | `auto_root_path` 可写性 | 彻底去掉用户填写（前端只读展示，后端 create/update 均不接受），只由初始化写入 |
| 5 | 目标目录已存在 | 同名覆盖、异名保留、不预清理 |
| 6 | pip 失败回滚 | 不回滚，保留代码 + 置 `failed` + 支持重试 |
| 7 | pip 源 | 不加镜像配置，直接用所选 `python_path` 的 pip 默认源 |

## 16. 遗留风险与后续可选项

| 项 | 说明 | 建议时机 |
| --- | --- | --- |
| 无初始化历史 | 只保留最近一次（§8.4） | 需要审计时再拆独立日志表 |
| 僵尸状态不自动复位 | 服务器重启可能卡在 `extracting`/`installing`（§14） | 参照 `SCHEDULER_ZOMBIE_TIMEOUT_HOURS` 做超时复位 |
| 残留文件不清理 | 重新初始化不会删除已从包中移除的老文件（§4.4） | 需要严格一致时改"先删后解压" |
| 无容器隔离 | pip 安装等于执行用户代码（§6.4） | 面向不可信用户时引入容器 |
| 临时目录残留 | 进程崩溃可能留下 zip/staging | 增加启动清理任务 |

## 17. 实现补充说明（编码期决策与验证记录）

以下是编码过程中相对本文档前文做出的补充/微调，均已落地：

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | 顶层散落文件 | 由"拒绝"改为"忽略 + 记日志"（§4.2 第 4 条）。这些文件本来就不会被投放，忽略比拒绝更不易误伤 |
