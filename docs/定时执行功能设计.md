## 1. 需求概述

### 1.1 背景

测试计划目前只能**手动**触发自动化用例执行（单个/批量/停止），无法按周期自动跑计划内的自动化用例。需要给计划增加"定时执行"能力，便于回归/冒烟等周期性自动化。

### 1.2 领域名词

| 名词 | 说明 |
| --- | --- |
| 定时执行任务（Schedule） | 归属于某个测试计划，含 cron 表达式、执行范围（全量/自定义子集）、启停开关 |
| cron 表达式 | 标准 5 段（分 时 日 月 周），可选 6 段（含秒）。分钟级精度即可满足 |
| 触发（fire） | 调度器发现"到点"且允许执行时，发起一轮计划批量执行 |
| 冲突跳过（skip） | 到点时该计划仍有执行在跑（手动批量或上一轮定时未结束），本轮跳过并记录原因 |

### 1.3 设计约束（来自历史经验，必须遵守）

1. **多 worker 进程内变量不共享**（gunicorn `--workers>1` 时 `_stop_batch_flags`/`_running_tasks` 各进程独立）：调度"到点判定"与"防重复触发"必须落到**数据库**，不能依赖进程内存。
2. **触发与执行分离**：调度器只负责"判定到点 + 认领任务（claim）+ 发起执行协程"，真正的用例执行复用现有 `auto_exec_service._execute_cases_sequential` 内核，不改执行逻辑。
3. 数据库时间继续使用 **offset-naive 本地时间**（`datetime.now()`），与全库现有约定一致；时区按服务器本地（Asia/Shanghai）。
4. 数据库迁移与初始数据遵循既有约定：**发布版本前压扁为唯一 alembic 迁移 + 唯一 seed_data**；开发期先加增量迁移与幂等 seed。

## 3. 数据模型设计

### 3.1 新表 `plan_schedules`

归属计划，一个计划可建多个定时任务。

```
plan_schedules
┌──────────────────┬───────────────────────────┬──────────────┬──────────────────────────┐
│ 字段             │ 类型                       │ 约束/默认     │ 说明                     │
├──────────────────┼───────────────────────────┼──────────────┼──────────────────────────┤
│ id               │ int                       │ PK 自增       │                          │
│ plan_id          │ int                       │ FK plans.id  │ 归属计划，CASCADE        │
│                  │                           │ index        │                          │
│ name             │ varchar(100)              │ not null     │ 任务名称                 │
│ cron_expr        │ varchar(50)               │ not null     │ 5/6 段 cron，后端 croniter│
│                  │                           │              │ 校验并算下次时间         │
│ mode             │ varchar(10)               │ not null     │ full=全量 / custom=子集  │
│                  │                           │ default 'full'│                          │
│ case_ids         │ JSONB                     │ null         │ mode=custom 时的用例 id   │
│                  │                           │              │ 列表；full 时为 null     │
│ enabled          │ boolean                   │ not null     │ 启停开关                 │
│                  │                           │ default true │                          │
│ description      │ text                      │ null         │ 说明                     │
│ is_running       │ boolean                   │ not null     │ 本轮是否正在执行         │
│                  │                           │ default false│                          │
│ running_since    │ timestamp(无时区)         │ null         │ 本轮开始时间（崩溃恢复）  │
│ last_run_at      │ timestamp(无时区)         │ null         │ 最近一次"实际触发"时间    │
│ last_status      │ varchar(10)               │ null         │ ok / skipped / error     │
│ last_skip_reason │ varchar(200)              │ null         │ 跳过/失败原因            │
│ next_run_at      │ timestamp(无时区)         │ not null     │ 下次应触发时间（调度依据）│
│ created_at       │ timestamp(无时区)         │ server now   │                          │
│ updated_at       │ timestamp(无时区)         │ server now   │                          │
└──────────────────┴───────────────────────────┴──────────────┴──────────────────────────┘
```

关键设计点：

- **`next_run_at` 是"调度依据"**：创建/编辑/每次触发完成时用 croniter 计算写入；调度循环只查 `enabled=true AND next_run_at<=now`。
- **防重复触发**：认领用**条件更新** `UPDATE plan_schedules SET is_running=true, running_since=now WHERE id=:id AND is_running=false AND next_run_at<=now`，受影响行数=1 才认领成功。多 worker 同时到点时只有 1 个 worker 认领成功，天然避免重复触发。
- **与手动执行冲突判定**：认领前额外检查该计划是否存在 `plan_testcases.result='running'` 的用例（手动批量执行会在开始时把所有用例置 running，执行中行数>0）。存在则**不认领**，改记 `last_status='skipped'` + `last_skip_reason='计划有执行在跑，本轮跳过'`，并推进 `next_run_at` 到下一个 cron 时刻。
- **崩溃恢复**：认领后若进程/worker 崩溃，`is_running` 会残留。调度循环对 `is_running=true AND running_since` 超过阈值（默认 4 小时）的任务判定为"僵尸"并复位（`is_running=false`，`last_status='error'`）。单个用例本身已有 120s 超时强杀，正常一轮批量不会超过该量级。

### 3.2 沿用现有表，不新增

- `plan_testcases`：结果/摘要/测试人（定时执行若未指定测试人则不写 tester_id）。
- `case_execution_logs`：每次执行的完整日志，与手动执行共用。
- `plans`：不改字段。

### 3.3 迁移与 seed 约定

- 开发期：新增 alembic 增量迁移建 `plan_schedules`；`scripts/seed_data.py` 幂等补充权限码与菜单按钮（见 §6）。
- 发布版本时（沿用现有压扁惯例）：把该表与全部权限合并进唯一 `0001_v1_0_0_initial.py`；老库按既有说明处理 `alembic_version`。
- 老库升级只需重跑一次 `seed_data.py`（幂等补新权限），不必清库。

## 4. 调度引擎设计（核心）

### 4.1 形态：内嵌应用进程（用户已确认）

调度器作为 **FastAPI lifespan 启动的后台 asyncio 任务**，随应用进程启动/停止，不加额外 systemd 单元。

- 每个 gunicorn worker 都会起一条调度循环 → 因此**"到点判定 + 认领"必须 DB 化**（§3.1 条件更新），保证多 worker 下也只会真正执行一次。
- 提供配置开关 `SCHEDULER_ENABLED`（默认 true）；测试/单测可关闭。

### 4.2 主循环

```
tick 间隔 30s（可配 SCHEDULER_TICK_SECONDS）
│
├─ 1. 僵尸复位：is_running=true 且 running_since 超过阈值 → 复位为 error（防崩溃残留）
├─ 2. 扫描候选：SELECT * FROM plan_schedules
│        WHERE enabled=true AND is_running=false AND next_run_at<=now()
├─ 3. 逐个认领（对每个候选）：
│     a. 先查冲突：该 plan 是否存在 result='running' 的计划用例？
│        是 → 记 skipped（last_status/last_skip_reason），next_run_at=下次 cron 时刻，continue
│     b. 条件更新认领：UPDATE ... SET is_running=true WHERE id=? AND is_running=false
│        （rowcount==1 才进入 c，否则说明已被别的 worker 认领，continue）
│     c. 发起执行：asyncio.create_task(run_schedule(schedule_id, db_factory))
└─ 4. 休眠到下一 tick
```

### 4.3 执行协程 `run_schedule(schedule_id)`

复用现有批量执行内核，不改 pytest 子进程与日志落库逻辑：

```
1. 取任务 + 计划 + 项目
2. 组装用例（与手动"批量执行"同规则）：
   - mode=full ：该计划下所有具备 module_code/case_code 的计划用例
   - mode=custom：case_ids ∩ 计划用例（已被移除/删除的自动忽略）
   - 空集 → 记 skipped（'无可执行用例'），收尾
3. 串行执行（复用 _execute_cases_sequential 内核）：
   每执行完一条 → 结果短摘要回填 plan_testcases + 完整日志写入 case_execution_logs
4. 收尾（无论成败）：
   - last_run_at=now, last_status=ok（全部执行完）
   - is_running=false, running_since=null
   - next_run_at = croniter.next(now)   # 推进到下一 cron 时刻
```

代码改动建议（最小侵入）：

- 现有 `plan_service.execute_auto_cases(plan_id, ptc_ids, current_user)` 里的"组装 entries + 全部置 running + create_task"逻辑抽成内部方法 `_prepare_plan_run(plan_id, ptc_ids, tester_id)`，手动执行与定时执行共用。
- 新增 `schedule_service.py`：任务 CRUD + cron 校验/算下次时间 + 认领/僵尸复位逻辑。
- 新增 `scheduler.py`：主循环 task；`main.py` lifespan 里 `asyncio.create_task(scheduler_loop())`，shutdown 时 cancel。
- 定时执行测试人：默认不指定（`tester_id=None`），结果记录为"定时触发"（后续如需展示来源，可在 `plan_testcases.result_desc` 摘要中带标记，见 §10）。

### 4.4 依赖

新增 `croniter`（纯 Python，含 python-dateutil 依赖）用于：

- cron 表达式合法性校验
- `next_run_at` 计算
- tick 的到点判定（也可直接用 `next_run_at<=now` 比较，不需每次逐分钟匹配）

不引入 APScheduler / Celery / 系统 crontab。

## 5. API 设计

> 全部挂在现有 plans 路由下；权限见 §6；统一响应包装沿用 `Response.success`。

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/plans/{plan_id}/schedules` | plan:schedule:list | 计划下定时任务列表（含 next_run_at/last_status） |
| POST | `/plans/{plan_id}/schedules` | plan:schedule:create | 创建（body 见下） |
| PUT | `/plans/{plan_id}/schedules/{schedule_id}` | plan:schedule:update | 编辑（名称/cron/范围/子集/说明） |
| PATCH | `/plans/{plan_id}/schedules/{schedule_id}/toggle` | plan:schedule:update | 启停 enabled |
| DELETE | `/plans/{plan_id}/schedules/{schedule_id}` | plan:schedule:delete | 删除 |
| POST | `/plans/{plan_id}/schedules/{schedule_id}/run-now` | plan:case:execute | 立即执行一轮（F6） |

创建/编辑请求体：

```jsonc
{
  "name": "每晚回归",
  "cron_expr": "0 2 * * *",          // 后端 croniter 校验
  "mode": "full",                     // full | custom
  "case_ids": [12, 34, 56],          // mode=custom 时必填；full 时忽略置 null
  "description": "每晚凌晨 2 点全量回归"
}
```

响应（列表项）：

```jsonc
{
  "id": 1, "plan_id": 2, "name": "每晚回归",
  "cron_expr": "0 2 * * *", "mode": "full", "case_ids": null,
  "enabled": true, "description": "...",
  "is_running": false,
  "last_run_at": "...", "last_status": "ok", "last_skip_reason": null,
  "next_run_at": "2026-09-08 02:00:00",
  "created_at": "...", "updated_at": "..."
}
```

校验规则：

- cron_expr 用 croniter 校验，非法直接 400。
- custom 模式 case_ids 至少 1 个，且每个 id 必须属于该计划（后端校验）。
- 计划需属于自动化执行可用项目（有 `auto_root_path`/`python_path`），否则创建即报错（与手动执行一致的前置校验）。

## 9. 部署与验证要点

- 部署：后端重启即生效（调度随 lifespan 起停）；无新增 systemd 单元。**多 worker 场景务必验证"到点只触发一轮"**（§4.2 条件更新 + 观察 case_execution_logs 条数）。
- 老库：`python -m scripts.seed_data` 补权限；新表走迁移。
- 验证矩阵：
  - cron 每分钟（`* * * * *`）与"每 2 小时"任务是否按时只触发一次；
  - 自定义子集只跑勾选用例；
  - 手动批量执行进行中到点 → 任务行 `last_status=skipped` 且不产生新执行日志；
  - 停用 enabled=false 后不再触发；再次启用正常；
  - 无 module_code/case_code 用例的 full 任务 → 触发后记 skipped（'无可执行用例'）；
  - 单个用例仍遵守 120s 超时；进程重启后僵尸任务能复位。

## 10. 结论与待确认项

1. **停止执行（已确认，无需改造）**：当前部署为单 worker（gunicorn `--workers 1`），UI"停止执行"与定时执行同进程共享 `_stop_batch_flags`，停止按钮对定时运行**同样生效**，无需 DB 化停止信号。仅当未来切换多 worker 时，才需要把停止信号落库（如 `plan_schedules.stop_requested` 或独立停止标记表），执行循环每用例前读 DB 判断。
2. **执行来源标识（已确认，不做）**：不区分手动/定时触发的结果与日志。
3. 计划生命周期状态 `plans.status`（not_started/in_progress/completed）本期不与定时执行联动；是否要在触发/结束时自动更新状态 → 待确认（不做默认不动）。
4. 僵尸复位阈值（默认 4h）与单次批量超长场景的平衡，可在实测后调整。
5. cron 时区：按服务器本地时间（Asia/Shanghai）计算，与库内 naive datetime 约定一致；若服务器时区非中国时区需另行处理。
