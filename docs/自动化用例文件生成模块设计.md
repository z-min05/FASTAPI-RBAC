## 1. 需求概述

### 1.1 业务场景

- 在管理系统的**项目维度**：增加一个**远程自动化测试根路径**配置项（非必填），填写格式如 `D:\zzm\pytestProject\test_framework_meterbot\tests`（对应 pytest `tests` 目录）。
- 在管理系统的**用例维度**：增加两个非必填字段：**模块编码**（与 `tests` 目录下 `.py` 文件名对应，不含后缀，如 `test_device_communication_log_page`）、**用例编码**（与 pytest 中函数名对应，如 `test_list_columns`）。
- 当满足以下条件时，**自动在远程路径生成 pytest 用例文件/函数骨架**，并自动写入 `@allure.title("{用例标题}")` 注解：
  1. 创建/编辑项目时填写了**自动化根路径**；
  2. 创建/导入用例时填写了**模块编码**和**用例编码**；
  3. 文件不存在则创建文件并写入必要头部导入与 `import allure`；文件已存在则追加 `def test_xxx(): ...` 函数，函数体包含前置条件/测试步骤/预期结果三行注释加 `pass`；
- **已有 class 结构保留**：你说明自动化用例中已有 `class TestXXX:`，后续仍由你手动维护，本系统**不写入、不修改**class 包裹，仅生成顶级函数即可。

### 1.2 核心约束

| 规则 | 说明 |
|---|---|
| 路径非必填 | 项目不配置则本模块不工作，不影响原有手动管理流程 |
| 编码非必填 | 单个用例不填模块编码/用例编码则跳过生成，不影响保存 |
| 仅生成骨架 | 不覆盖已有函数，仅当**函数不存在时**追加；不删除、不修改已有内容 |
| 不修改 class | 只生成独立顶级 `def test_func():`，不套 class；已有 class 你手动维护 |
| 路径校验 | 项目配置路径不存在或不可写时返回友好错误，不影响项目保存 |
| 文件名约定 | 模块编码 → `{自动化根路径}/{模块编码}.py`，模块编码不允许包含 `../` 等路径越界字符 |

### 1.3 映射关系

```
项目.auto_root_path → D:\zzm\pytestProject\test_framework_meterbot\tests
           ↓
用例.module_code → tests/{module_code}.py （文件名就是模块编码，如 test_device_communication_log_page.py）
           ↓
用例.case_code   → 函数名就是用例编码，如 test_list_columns
```

## 2. 数据模型变更

### 2.1 `projects` 表：新增字段

| 字段 | 类型 | 约束/默认 | 说明 |
|---|---|---|---|
| `auto_root_path` | `String(500)` | NULL（非必填） | 远程 pytest `tests` 目录绝对路径 |

> 说明：项目模块在 `projects` 表原有基础上**增量加列**，所有已有项目自动为 NULL，不影响存量数据。

### 2.2 `testcases` 表：新增字段

| 字段 | 类型 | 约束/默认 | 说明 |
|---|---|---|---|
| `module_code` | `String(100)` | NULL（非必填） | 模块编码 → 对应 `tests` 目录下的 `.py` 文件名（不含 `.py` 后缀） |
| `case_code` | `String(100)` | NULL（非必填） | 用例编码 → 对应 `.py` 文件中的 pytest 函数名 |

> 说明：仅加列，原有用例自动为 NULL；模块编码+用例编码同时非空才触发生成，一个模块编码可对应多个用例编码（多个函数在同一个 `.py` 文件）。

### 2.3 唯一性约束

在 `testcases` 表上增加**唯一索引约束**：`UNIQUE(project_id, module_code, case_code)` WHERE `module_code IS NOT NULL` AND `case_code IS NOT NULL`。  
即：**同一个项目下，`(module_code, case_code)` 组合必须唯一**；任一为 NULL 不参与唯一检查。

## 3. 文件生成规则

### 3.1 路径合法性校验

1. **目录存在**：`auto_root_path` 必须是已存在的目录；不存在则报错（不影响项目保存，仅提示用户修正路径）。
2. **目录可写**：尝试创建空临时文件验证写入权限；不可写则报错。
3. **文件名安全**：`module_code` 仅允许字母、数字、下划线 `_`、短横线 `-`，必须以 `test_` 开头（符合 pytest 对文件名的约定）；不允许包含 `/ \ ..` 等会导致路径越界的字符；禁止以 `..` 开头或包含 `../`。
4. **函数名安全**：`case_code` 仅允许字母、数字、下划线 `_`，必须以 `test_` 开头（符合 pytest 约定）。

### 3.2 文件写入规则

| 场景 | 行为 |
|---|---|
| 文件不存在 | 1. 创建文件<br>2. 写入头部：`import pytest\nimport allure\n\n`（留两个空行）<br>3. 追加函数（见下文） |
| 文件已存在 | 1. 读取整个文件内容到内存<br>2. 检查是否已有同名函数：按行搜索，若存在以 `def {case_code}(` 开头的行则直接返回成功（不覆盖，不重复生成）<br>3. 不存在则在文件**末尾**空两行后追加新函数 |

### 3.3 函数骨架格式

```python
@allure.title("{用例标题}")
def {case_code}():
    # 前置条件：{precondition}
    # 测试步骤：
    # {steps}
    # 预期结果：{expected_result}
    pass
```

> 示例：
> - 用例标题：`设备日志页面正常加载，列表展示设备SN...`
> - 前置条件：`用户已登录，进入设备通信日志页面`
> - 测试步骤：`1. 页面加载完成 2. 查看列表列`
> - 预期结果：`列表包含所需列`
>
> 生成代码：
>
> ```python
> @allure.title("设备日志页面正常加载，列表展示设备SN、通信方向、动作类型、状态、原始报文、创建时间")
> def test_list_columns():
>     # 前置条件：用户已登录，进入设备通信日志页面
>     # 测试步骤：
>     # 1. 页面加载完成 2. 查看列表列
>     # 预期结果：列表包含设备SN、通信方向、动作类型、状态、原始报文、创建时间
>     pass
> ```

### 3.4 异常处理策略

- 路径不合法/不可写：返回 400 错误，给出明确提示（如"自动化根路径不存在，请检查配置"），但不阻断项目/用例保存；
- 模块编码/用例编码格式非法：返回 400 错误，不阻断保存，提示格式要求；
- 文件已存在同名函数：静默成功，不报错、不覆盖；
- 磁盘IO错误（如空间满、权限不足）：返回错误但仍保存用例记录（仅文件生成失败）。

## 4. API 接口设计

### 4.1 项目接口变更

| 位置 | 变更 |
|---|---|
| `ProjectBase`（schema） | 新增 `auto_root_path: str | None = Field(None, max_length=500)` |
| `ProjectCreate` / `ProjectUpdate` | 继承 `ProjectBase`，自动带该字段 |
| `ProjectResponse` | 新增该字段回显 |

接口行为：
- 创建/更新项目时，若 `auto_root_path` 不为空则**仅校验路径存在+可写**，不生成任何文件（文件生成仅在用例创建/导入时触发）。

### 4.2 用例接口变更

| 位置 | 变更 |
|---|---|
| `TestCaseBase`（schema） | 新增：<br>`module_code: str | None = Field(None, max_length=100)`<br>`case_code: str | None = Field(None, max_length=100)` |
| `TestCaseCreate` / `TestCaseUpdate` | 自动带上述两个字段 |
| `TestCaseResponse` | 新增两个字段回显 |

接口行为（**创建用例** `POST /testcases`）：

- 若满足：项目配置了 `auto_root_path`，且当前用例 `module_code` 和 `case_code` 均非空 → 触发文件生成（按上述写入规则）；
- 文件生成失败返回明确错误，但**用例记录仍保存成功**；前端可选择显示警告但不阻断操作。

接口行为（**批量导入用例** `POST /testcases/import`）：

- 导入模板新增两列（非必填）：`模块编码`、`用例编码`；
- 每条记录满足条件（项目有路径+两个编码都填）则逐条尝试生成；
- 单个文件生成失败仅计入 `failures`（添加错误信息到结果中），不阻断其他记录导入。

接口行为（**编辑用例** `PUT /testcases/{id}`）：

- 若修改后 `module_code` 和 `case_code` 同时非空 → 触发文件生成（同新建规则，只在不存在时生成，不覆盖）；
- 若修改了 `module_code` 或 `case_code`，旧路径/旧函数不删除（由用户手动清理），仅在新位置生成。

## 9. 与现有 pytest 框架适配说明

你现有框架已使用：

```python
import allure

@allure.epic("补充用例")
@allure.feature("设备日志")
class TestDeviceLog:
    @allure.story("日志列表")
    @allure.title("设备日志页面正常加载...")
    def test_list_columns(self, device_communication_log_page):
        ...
```

本系统生成逻辑为：

- **不碰 class**：只生成顶层独立函数 `def test_xxx():`，不套入任何 class；
- 你拿到生成的骨架后，手动剪切进 class 并添加 `@allure.story` / fixture 参数即可；
- 本系统**永远不会删除或修改你已手写完成的代码**，仅在文件末尾追加新骨架。
