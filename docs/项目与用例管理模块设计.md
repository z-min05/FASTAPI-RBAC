## 1. 项目总体设计

### 1.1 项目背景与目标

FastAPI-RBAC 是一个基于 **FastAPI + SQLAlchemy(异步) + PostgreSQL + Redis + Casbin** 的 RBAC（基于角色的访问控制）权限管理系统，提供完整的用户、角色、权限、菜单、部门、操作日志管理能力，并在前端提供对应管理界面。

目标：

- 提供可复用的**三级权限模型**：API 接口权限、菜单权限、按钮权限；
- 支持**多 Worker 部署**下的策略一致性（Redis 版本号广播）；
- 提供**首次启动自动初始化**能力：自动建表 + 写入内置权限/菜单/角色/用户种子数据；
- 预留业务模块（如本文档第 3 章的用例管理模块）的标准化接入方式。

### 1.3 系统架构

采用分层架构，请求自上而下经过：

```
HTTP 请求
   │
   ▼
中间件（CORS / Logging 日志中间件）
   │
   ▼
路由层 app/api/v1/*（参数校验、依赖注入：认证 + 权限校验）
   │
   ▼
服务层 app/services/*（业务规则、事务编排）
   │
   ▼
仓储层 app/repositories/*（数据访问，复用 BaseRepository 通用 CRUD）
   │
   ▼
模型层 app/models/*（SQLAlchemy ORM，BaseModel 提供 id/created_at/updated_at）
   │
   ▼
PostgreSQL / Redis（Casbin 策略表、策略版本号）
```

关键设计点：

- **依赖注入**：`get_db` 提供会话；`require_permissions("module:action")` 完成登录态 + API 权限校验；
- **统一响应**：`{ code, message, data }`（见 `app/core/response.py`）；
- **统一分页**：`PaginationParams(page, page_size)` + `PaginatedResponse{items,total,page,page_size,total_pages}`（见 `app/core/pagination.py`）；
- **统一异常**：`AppException` 体系（BadRequest/Unauthorized/Forbidden/NotFound/Conflict 等）+ 全局异常处理器。

### 1.5 权限体系设计（Casbin 三级权限）

系统采用 **Casbin RBAC + 域(dom)** 实现三级权限控制，策略持久化到 PostgreSQL 的 `casbin_rule` 表（由 casbin-sqlalchemy-adapter 自动建表）。

| 域 dom | 含义 | obj | act |
|---|---|---|---|
| `api` | API 接口权限 | 权限编码（`module:action`） | access |
| `menu` | 菜单权限 | 菜单路径（`/system/users`） | access |
| `button` | 按钮权限 | 权限编码 | click |

数据来源与策略生成：

- **Permission 表** → 生成 `p, role:{code}, api, {code}, access`（API 权限）；
- **Menu 表（menu_type=directory/menu）** → 生成 `p, role:{code}, menu, {path}, access`；
- **Menu 表（menu_type=button）** → 生成 `p, role:{code}, button, {permission}, click`；
- **用户-角色** → 生成 `g, user:{id}, role:{code}, {dom}` 继承关系。

核心流程（`app/core/casbin_service.py`）：

1. `sync_policies(db)`：批量预加载角色/用户-角色/权限/菜单关联，构建**新 Enforcer**，原子替换旧引用（双缓冲，避免策略真空），并持久化到 `casbin_rule`；
2. `_bump_policy_version()`：策略变更后递增 Redis 键 `casbin:policy_version`，通知其他 Worker；
3. `_check_policy_version()`：请求/启动时比对本地版本号，过期则 `load_policy()` 重载；
4. 校验入口：`check_api_permission / check_menu_permission / check_button_permission`，超管（`is_superuser`）直接放行。

权限编码约定：`模块:操作`，例如 `user:list`、`role:create`、`log:list`。

### 1.6 认证流程

```
POST /api/v1/auth/login  { username, password, captcha_key, captcha_code }
   → 校验验证码（Redis）→ 校验用户名密码（bcrypt）→ 签发 JWT
   → 返回 { access_token, refresh_token }
```

- Access Token（默认 30 分钟过期）用于接口鉴权；
- Refresh Token（默认 7 天）用于续期；
- 登录后前端调用 `/auth/me` 获取 `user / menus / api_permissions / button_permissions`，驱动动态菜单与按钮级权限控制。

- 采用**单一基础迁移** `0001_init_rbac_tables.py`（已重写，覆盖当前全部 RBAC 表）；
- 新增业务模块时：`alembic revision --autogenerate -m "..."` 生成增量迁移。

### 1.8 首次启动初始化流程

应用启动（`main.py` lifespan）依次执行，任一环节失败仅告警不阻塞启动：

```
1) init_db()  ──► 创建全部表（Base.metadata.create_all）
   │
   └──► 若 users 表为空，写入内置种子数据：
         ├── 21 个 API 权限（user/role/permission/menu/department/log 模块）
         ├── 15+ 个菜单（仪表盘、系统管理目录 + 6 个子菜单 + 各子菜单按钮）
         ├── 2 个角色（admin 超管 / user 普通用户）
         ├── 2 个用户（admin/admin123456, user/user123456）
         └── 1 个根部门（总公司 HQ）
   │
2) ensure_policy_loaded(db)
   │  ├── 初始化 Casbin Enforcer（PostgreSQL 适配器，失败回退内存模式）
   │  └── sync_policies 同步策略到 casbin_rule
   │
3) 应用就绪，对外提供服务
```

手动重置（开发用）：`python -m scripts.seed_data --reset`（drop_all → 建表 → 种子 → Casbin 同步）。

> 种子数据与启动初始化共用同一份逻辑（`app/db/init_db.py` + `app/db/seed.py`），保证 CLI 与启动行为一致。

### 1.9 多 Worker 一致性

- 策略写入通过 PostgreSQL `casbin_rule` 持久化，任意 Worker 均可重载；
- 策略变更时递增 Redis `casbin:policy_version`；
- 其他 Worker 在请求处理前比对版本号，发现变更即 `load_policy()` 热更新，无需重启。

### 1.10 前端架构

- Vue 3（Composition API）+ Vite + Pinia + Vue Router 4 + Ant Design Vue 4；
- 请求封装：`src/api/index.js`（axios 实例，自动携带 Token、统一错误处理），业务接口按模块放 `src/api/*.js`；
- 状态管理：`src/stores/auth.js`（登录态、菜单、API/按钮权限）；
- 菜单：后端动态下发（`/auth/me`），`MainLayout.vue` 按 目录/菜单 两级渲染；
- 按钮级权限：通过 `api_permissions / button_permissions` 控制页面内按钮显隐；
- 路由：`src/router/index.js` 静态注册页面路由，与后端菜单路径一一对应。

## 2. 项目管理与用例管理模块设计

### 2.1 需求概述

在现有 RBAC 系统中新增**项目管理 + 用例管理**模块。**项目**是业务对象的容器，**用例按项目划分**（每条用例必须归属一个项目），用于沉淀、维护、检索和追溯测试用例，满足以下测试管理诉求：

- 以**项目**为组织单元管理用例，支持按项目切换与筛选；
- 用例在项目内**按模块划分**，支持按模块检索与统计；
- 用例**来源可追溯**（需求/接口文档等），保证"用例合理、有依据、全覆盖"；
- 用例具有**优先级**，关键链路（业务数据传输/接收、成功/异常场景、成功率等）优先保障；
- 权限受控：不同角色拥有不同项目/用例操作权限（查看/新增/编辑/删除/导入导出）。

> 本期**仅做用例管理**，不包含用例执行、结果回填等功能。

### 2.2 功能清单

**项目：**

| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 项目列表 | 分页 + 关键字搜索 + 启用状态筛选 |
| F2 | 新增/编辑/删除项目 | 项目基础信息维护；删除前校验是否存在关联用例 |
| F3 | 全部项目下拉 | 不分页列表，供用例页"项目"筛选使用 |

**用例：**

| 编号 | 功能 | 说明 |
|---|---|---|
| F4 | 用例列表 | 分页 + 多条件筛选（项目/模块/优先级/状态/来源/关键字）+ 排序 |
| F5 | 用例详情 | 查看用例完整信息 |
| F6 | 新增用例 | 录入所属项目、标题、模块、优先级、类型、来源、前置条件、步骤、预期结果等 |
| F7 | 编辑用例 | 修改用例（记录 updated_at） |
| F8 | 删除用例 | 单条删除 / 批量删除 |
| F9 | 模块管理 | 从既有用例中提取模块列表，供筛选与统计 |
| F10 | 导入 / 导出 | CSV 导入导出 |

### 2.3 数据模型设计

**表名：`projects`**（继承 `BaseModel`：id / created_at / updated_at）

| 字段 | 类型 | 约束/默认 | 说明 |
|---|---|---|---|
| code | String(50) | NOT NULL, unique | 项目编码 |
| name | String(100) | NOT NULL | 项目名称 |
| description | Text | NULL | 项目描述 |
| owner_id | Integer | NULL | 负责人 user_id（可选） |
| is_active | Boolean | NOT NULL, default True | 启用状态（停用的项目不可新增用例） |

**表名：`testcases`**（继承 `BaseModel`：id / created_at / updated_at）

| 字段 | 类型 | 约束/默认 | 说明 |
|---|---|---|---|
| project_id | Integer | NOT NULL, FK→projects.id, index | 所属项目（用例按项目划分） |
| title | String(200) | NOT NULL | 用例标题 |
| module | String(50) | NOT NULL, index | 所属模块（项目内按模块划分用例） |
| priority | String(10) | NOT NULL, default 'P1' | 优先级：P0/P1/P2/P3 |
| case_type | String(30) | NOT NULL, default 'function' | 用例类型：function/interface/performance/compatibility/security 等 |
| source | String(50) | NULL | 来源：需求文档/接口文档/经验总结 等（保证用例有据可依） |
| precondition | Text | NULL | 前置条件 |
| steps | Text | NULL | 测试步骤（多行，建议编号） |
| expected_result | Text | NOT NULL | 预期结果 |
| status | String(20) | NOT NULL, default 'draft' | 管理状态：draft(草稿)/reviewed(已评审)/archived(已归档) |
| tags | String(200) | NULL | 覆盖点/关键词标签（逗号分隔，辅助覆盖度检查） |

设计说明：

- 用例必须归属项目（`project_id NOT NULL`）；删除项目前校验是否有关联用例，有则返回冲突（409）禁止删除；
- 本期为**纯管理态**：不包含实际结果/过程记录/执行时间等执行字段；后续需要执行功能时，再扩展 `testcase_executions` 表（id, testcase_id, status, actual_result, process_record, run_by, created_at）实现历史追溯，不改动本表；
- `status` 仅表示管理生命周期（草稿/已评审/已归档），与执行结果无关；
- 枚举值建议收敛在 `app/core/constants.py` 或 schema 内（priority/status/case_type），前端下拉同步；
- `steps`、`precondition`、`expected_result` 用 `Text` 保存，每行一条步骤，支持前端文本域编辑。

### 2.4 API 接口设计

统一前缀 `/api/v1`，鉴权方式：`Bearer Token` + `require_permissions(...)`。

| PUT | /projects/{id} | project:update | 编辑项目 |

交互要点：

- 用例页"项目"筛选项来自 `/projects/all`，"模块"筛选项来自 `/testcases/modules?project_id=`；
- 优先级展示为彩色标签：P0 红 / P1 橙 / P2 蓝 / P3 灰；
- 状态展示为标签：草稿灰 / 已评审蓝 / 已归档紫；
- 新增/编辑使用 Drawer 表单（所属项目下拉 + 步骤/前置条件/预期结果 多行文本域）；
- 删除项目时后端校验存在关联用例则报 409，前端提示"请先删除该项目下的用例"；
- 按钮显隐由 `buttonPermissions` 控制（v-if="hasBtn('testcase:create')"）；
- 请求封装：`frontend/src/api/project.js`、`frontend/src/api/testcase.js`。

### 2.7 导入导出设计

数据列定义（导入导出共用，模板与导出按此列输出）：

```
项目编码,标题,模块,优先级,类型,来源,前置条件,步骤,预期结果,状态,标签
```

- **导入模板**：下载为 xlsx（`testcase_import_template.xlsx`）。表头直接在列名后标注必填/选填（`项目编码（必填）`、`优先级（非必填）` 等），表头加粗、"必填"红色；必填列：项目编码、标题、模块、预期结果；
- **导入**：支持 CSV / xlsx；按"项目编码"匹配项目（不存在则在失败明细中提示该行），逐行校验必填字段（项目编码/标题/模块/预期结果），`priority/status/case_type` 做白名单校验，返回成功条数与失败行明细；
- **导出**：按当前筛选条件输出全部数据为 CSV（UTF-8 带 BOM），Excel/WPS 可直接打开。

## 3. 附录：通用约定

- **响应格式**：`{ code, message, data }`，成功 code=200；错误 code 取 4xx/5xx；
- **分页参数**：`page`（默认 1）、`page_size`（默认 10，最大 100）；
- **认证头**：`Authorization: Bearer <access_token>`；
- **权限依赖**：`require_permissions("testcase:list", ...)`（多权限任一满足即可）；超管自动放行；
- **命名规范**：权限编码 `模块:操作`；菜单 path `/模块/资源`；组件路径 `模块/页面名`；
- **数据库变更**：一律通过 Alembic 迁移，不手工改库。
